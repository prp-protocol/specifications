D. Purpose:
   Associate a DNS name with one or more typed PRP references independently of
   machine location or IP addressing. References can identify a principal,
   discovery alias, multicast or groupcast. DNS authenticates publication but
   grants no class-specific authority. No reverse mapping.
E. Definition:
   Proposed specification: specifications/prp-dns-reference-rr-v1.md, revision 10.
   Normative dependency: the canonical reference envelope, four class codes and
   closed suite-to-identifier-length table reproduced in the proposal. The DNS
   format treats every identifier as opaque. Class-specific formation,
   authority and lifecycle specifications are not required to implement DNS
   storage, presentation or unknown-RR forwarding.
   DNS class IN; ordinary data RR. RDATA is the complete canonical reference:
   header(u8), reference suite(u16 network order), exact suite-sized identifier.
   Header bits1..0 encode class; bits7..2 MUST be zero. Complete valid headers
   are IDENTITY=0x00, ALIAS=0x01, MULTICAST=0x02 and GROUPCAST=0x03. Reference
   class differs from DNS class IN.
   Current lengths35/51. No version, identifier-length or representative field.
   Presentation: decimal reference class, decimal suite, hexadecimal identifier;
   class is decimal0..3. No class-less or version-prefixed fallback.
   No compression, names, addresses, optional fields or additional processing.
   An RRset MAY contain multiple distinct references. Identical duplicates add
   no reference. DNS order expresses no priority, preference, fallback or
   rotation; applications select only a requested supported class under explicit
   policy. No server-specific cardinality enforcement is required.
   RRset changes prove no migration, delegation or equivalence. Still-valid
   cached bindings may remain usable. DNS changes do not revoke identities,
   groups, streams, relationships or sessions and do not override independent pins.
   DNSSEC is not a latest-version proof; replay and serve-stale limitations are
   explicit. DNAME synthesis and wildcard expansion follow DNSSEC validation.
F. Alternatives:
   TXT can carry conventions; URI can express URI discovery. A dedicated RR
   is requested for a typed binary reference association without locator or
   priority semantics. HIP has protocol-specific identifiers/key formats and
   cannot use PRP suite values without changing its meaning. A/AAAA locate IP
   endpoints rather than PRP participants. See proposal section 6.
G. Preferred mnemonic: PRP. Numeric code: assigned by IANA, no preference.
H. Registry dependencies:
   Uses the canonical PRP class map and closed reference-suite length set, not
   DNSSEC algorithm numbers. These values are defined directly in the proposed
   RR specification. Class-specific PRP documents govern use after selection
   but do not alter the DNS RDATA grammar. This working draft is not wire
   admission. No new IANA subregistry is requested.
   REG-001 is separate PRP governance work, not an automatic DNS submission gate.
I. Unknown-type handling:
   Compatible with RFC 3597. No special server/resolver processing required.
   Type-aware presentation and application consumption are needed for use.
